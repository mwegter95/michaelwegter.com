The workflow you described

Every engine in the demo supports this exact loop. Approval is a hard gate: outputs cannot push to any destination until you explicitly click Approve.

01
Run
User fills the brief and fires an engine
02
Generate
LLM router routes and returns structured output
03
Review
Output lands in Pending Review queue, status: needs-review
04
Revise
User requests edits; engine re-runs with revision notes
05
Approve
User clicks Approve; status flips to approved
06
Save / Push
Push button unlocks; output saved to destination

Backend LLM routing layer

The frontend never calls OpenAI, Claude, or any provider directly. It calls a provider-agnostic LLMRouter. Adding a second provider is one config entry, not a rebuild.

Request flow

Frontend Next.js / React iframe
POST /route { engine, payload, workspace_id }
LLM Router selects model from config registry
Provider API OpenAI / Claude / local model
Supabase log run_id, model, tokens, cost, status

Frontend

Next.js / React, embedded in GoHighLevel via iframe custom menu page. Calls only the backend router, never any LLM provider.

LLM Router

AWS Lambda + API Gateway (or Next.js API route). Provider-agnostic contract: engine name + payload in, normalized output + run metadata out.

Data Layer

Supabase (Postgres + Auth + RLS). Runs, outputs, usage logs, workspace isolation. Your existing Supabase investment carries forward.

Integrations

Google Drive API + GitHub API, server-side OAuth. LinkedIn + X push via approved APIs. Frontend sees only receipts, never API keys.

Approval gating, not just a UI pattern

Two independent layers prevent unapproved outputs from publishing, sending, or saving to connected systems.

Frontend status machine

Every output has a status field. The Push/Save button is rendered disabled and cursor: not-allowed unless status is exactly "approved". There is no code path that advances an output to "pushed" without an explicit user click on Approve. You can verify this in the demo: try clicking Push before Approve.

Backend guard (production)

The backend's push endpoints check the output's status in Supabase before executing. A 403 is returned if status is not "approved", even if a client somehow bypasses the frontend gate. Frontend and backend enforce the same rule independently.

Output status lifecycle

generating  engine is running
needs-review  output ready, no action yet
revised  revision requested, re-running
approved  user approved, push unlocked
pushed  saved to destination
